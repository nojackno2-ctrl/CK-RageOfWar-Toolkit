# CVXVisible sidecar 重導向完整性稽核（2026-08-21）

對象：`src/CKPerf/hires.cpp`（未提交）。方法：對磁碟上實際執行的
`Celtic kings.exe` 做 capstone 線性掃描（含失敗重新同步，1,112,279 條指令），
以 call target 推導函式邊界，再比對每一處 16-byte 槽位定址計算。
稽核腳本在 session scratchpad：`ck.py` / `funcs.py` / `sweep3.py`。

## 已確立的事實

- **`0x00798C64` 就是 CVXVisible 全域指標。** 配置點 `0x0056FE10` 內
  `push 0x510` 後 `0x0056FE85 mov [0x798c64], eax`；解構時 `0x0056FF67` 寫回 0。
- 內嵌槽位陣列位於 `object+0x10 .. +0x4BF`（75 * 16 bytes），
  其後 `+0x4C0..+0x50F` 為 live bounds 與三個容器。
- `object+0x4C8` 與 `object+0x4CC` 各存放一個**外部** vector 的起始指標，
  與內嵌陣列是不同的儲存區。

## 槽位定址計算的完整清單

在 9 個相關函式中，符合「`shl reg,4` 後數條內與某基底合併」的站點共 36 處。
其中 30 處已由 `kRedirects` / merge cave / clear cave 處理，**6 處未處理**：

| 位址 | 形式 | 基底來源 | 判定 |
|---|---|---|---|
| `0x00479717` | `lea edi,[esp + ecx + 0xd4]` | **堆疊區域變數** | 待查框架大小 |
| `0x0047A49E` → `0x0047A4A1` | `lea ebx,[ecx + edx + 0x18]` | `edx` = 物件基底 | **內嵌陣列，必須重導向** |
| `0x0047A7F1` | `add ebx,ebp` | `ebp = [edi+0x4C8]` | 外部 vector，待查容量 |
| `0x0047A802` | `lea ebx,[ebx+ebp+0xf]` | `ebp = [edi+0x4C8]` | 外部 vector，待查容量 |
| `0x0047A814` | `add ebx,ebp` | `ebp = [edi+0x4CC]` | 外部 vector，待查容量 |
| `0x0047A822` | `lea ecx,[ecx+ebx-1]` | 承上 `+0x4CC` 鏈 | 外部 vector，待查容量 |

## 缺陷 1（嚴重，會損毀記憶體）— `0x0047A020` 的迴圈

`kConsumerLimits` 已把 `0x0047A489` 與 `0x0047A7A4` 兩處 `cmp ecx,75` 提高到 127，
但同一迴圈的槽位指標仍走內嵌陣列：

```
0047A49A  mov edx, [esp+0x14]          ; edx = 物件基底
0047A49E  shl ecx, 4                   ; index*16
0047A4A1  lea ebx, [ecx + edx + 0x18]  ; = base + 0x18 + index*16
...迴圈本體寫 [ebx-8] [ebx-4] [ebx] [ebx+4]，每圈 add ebx,0x10
```

`lea` 的三運算元形式不符合 `kRedirects` 所要求的「span 以兩位元組 `add indexReg,thisReg` 結尾」，
因此既沒有被列入重導向，`ValidateAll()` 也不會察覺。

後果：容量 > 2400 時本迴圈跑 127 圈，第 75..126 圈每圈寫 16 bytes 進
`object+0x4C0` 起，輾過 tail members 後再衝出 `0x510` 配置尾端約 944 bytes。
**這比 producer-cap 版本更危險**：producer cap 只是畫面錯，這個是堆積損毀。

## 缺陷 2（正確性）— `0x00478840` 的四個站點被跳過

`HighResolutionInstallDeferred()` 的迴圈從 `redirectIndex = 4` 開始，
註解稱這四處「物件身分未證實」。身分現在證實了，它們就是同一個物件：

```
00478852  mov edi, [0x798c64]              ; 全域 CVXVisible
0047889F  call 0x47abf0                    ; ecx = edi，即 producer
004788B4  mov dword ptr [edi+0x4c0], 1     ; 寫 tail member
004788D2  shl esi,4 / add esi,edi          ; 槽位寫入，走內嵌陣列
```

四處（`0x004788D2`、`0x0047891C`、`0x00478A3A`、`0x00478A86`）都以
`[r] [r+4] [r+8] [r+0xC]` 寫滿一個 16-byte 槽位。它們寫內嵌陣列，
而所有已重導向的 consumer 讀 sidecar——**寫入與讀取分屬兩塊儲存區**。
這正好會產生「部分欄位資料缺失／殘留」的畫面症狀，
且 index >= 75 時同樣覆寫 `+0x4C0..+0x50F`。

## 缺陷 3（待查）— 被提高的上限所連帶影響的其他儲存區

`kConsumerLimits` 提高的五處上限中，涉及的迴圈另外還會走：

- `0x00479400` 內 `lea edi,[esp + ecx + 0xd4]` 的堆疊區域陣列
- `object+0x4C8` / `object+0x4CC` 指向的兩個外部 vector

若這兩者也是依 75 槽配置，提高到 127 會分別造成堆疊溢位與堆積溢位。
**必須先確認容量，再決定是擴充、或是這些迴圈不得提高上限。**

## 結論

現行 `hires.cpp` 在容量 > 2400 時不可用於實機測試，會損毀記憶體。
修正順序：缺陷 1 →缺陷 2 →缺陷 3 的容量確認。

## 缺陷 3 的追查結果（2026-08-21，稍後補入）

### 3a — 堆疊區域陣列：**已排除，無風險**

`0x00479400` 開頭為 `mov eax,0x20c4` / `call 0x006DB6B0`（`__chkstk`），
框架 8,388 bytes。陣列自 `esp+0xd4` 起，可用 8,176 bytes = **511 個 16-byte 槽位**。
127 槽遠低於此。且此函式本來就依視埠寬度生成，堆疊是照大視埠設計的，
這也是 2048x1152 無需任何 runtime patch 即可運作的原因之一。

### 3b — `+0x4C8` 不是兩個陣列，是**一個動態容器**

先前把 `+0x4C8` 與 `+0x4CC` 讀成兩個獨立陣列基底，是錯的。
`0x00479466 lea edi,[esi+0x4c8]` 與 `0x0047A04E lea eax,[ebp+0x4c8]` 會取其位址
交給容器方法；`0x0047A846` 另讀 `+0x4D0`。三個指標連續排列，
即 `begin = +0x4C8`、`end = +0x4CC`、`capacity_end = +0x4D0` 的標準三指標容器。
建構子 `0x00478AD0` 把三者都初始化為 0，之後由容器操作成長。

因此它**沒有寫死的 75 容量**，不會像內嵌陣列那樣被寫爆。

### 3c — 「常數 127 是否安全」：**已查證，安全**

先前擔心把上限改成常數 127 會讓走 `+0x4C8` 容器的迴圈越過 `end`。查證後不成立。

五個被提高的上限全部位於 `0x0047A020`，且都作用在走 sidecar 的迴圈上：

| 上限 | 性質 | 迴圈本體走哪 |
|---|---|---|
| `0x0047A097` | `cmp esi,75` / `jge` | `0x0047A0A2 inc esi / shl esi,4 / add esi,ebp` — 即已重導向的 `0x0047A0A3`，走 sidecar |
| `0x0047A0C3` | `cmp edi,75` / `jge` | `0x0047A0C0 add esi,0x10` 步進同一指標，走 sidecar |
| `0x0047A115` | `cmp edi,75` / `je` | 非迴圈上限，是對同一計數器的相等性終止判定 |
| `0x0047A489` | `cmp ecx,75` / `jge` | 指標由 `0x0047A4A1` 初始化 —— 缺陷 1 修好後走 sidecar |
| `0x0047A7A4` | `cmp ecx,75` / `jl` | `0x0047A7A1 add ebx,0x10` 步進同一指標，走 sidecar |

而 `+0x4C8` 容器的存取（`0x0047A7E9` 起）位於**迴圈結束之後**，只執行一次，
由 `[esp+0x1c]`、`[esp+0x24]`、`[esp+0x18]` 等獨立索引驅動，
不受這五個上限影響。每幀清除已把 127 個 sidecar 槽位全部歸零，
因此多跑的圈數讀到的是零值，行為確定。

附帶一提：`0x0047A122` 原版就存在 `cmp esi,0x7f`（127），
是另一張 128 筆表格的既有上限，與本修補選用 127 無關，純屬巧合。

## 收尾更正：`+0x4C8` 容器模型被實機記憶體讀取推翻（2026-08-21 傍晚）

本文件到此為止的所有段落，包括「缺陷 3b／3c」的查證與稍早遙測量出的
「1,171～1,286 個矩形」，都建立在一個假設上：`CVXVisible+0x4C8` 是
begin/end/capacity 三指標的矩形容器。

**這個假設是錯的。** 2026-08-21 傍晚以除錯器附加到執行中的遊戲行程，
直接讀取 `CVXVisible` 物件記憶體，結果：

```
+0x4C0:      0      0    1692   17151
+0x4D0:   4251  18456       0       0
+0x4E0:  32735  22880  0x1989C138  0x1989C14C   <- 真正的指標從這裡開始
+0x4F0:  0x1989C14C  0x1989C150  0x1989C164  0x1989C164
+0x500:  0x19903E98  0x19903EAC  0x19903EAC       5        <- +0x50C 元素數
```

`+0x4C8`／`+0x4CC` 讀到的是普通座標數值（1692、17151），不是指標。
真正的三個指標容器在 `+0x4E8`、`+0x4F4`、`+0x500`，且各自只有 5 個
4-byte 元素——不是矩形陣列，是別的東西（尚未確認用途）。

連帶地，`sidecar` 本身（無論是原本 127 格還是後來擴容到 2342 格）在
實機遊玩中全程量到 **0 / 2342 個非零槽位**，即使畫面正在渲染、
重導向站點也確實觸發了數千次。也就是說：sidecar 容量、欄位上限
（site F / `g_columnCap`）、表面尺寸（`g_surfaceWidth`）這三輪修補
全部針對一個不存在的瓶頸，沒有解決任何實際問題。它們不是有害的
（仍受 `ValidateAll()` 位元組驗證保護，不寫入即拒絕），但也不是有效的。

**唯一被獨立證實有效的是缺陷 1／缺陷 2 的閃退修復**（本文件前半段所述，
`kMergeSite3 = 0x0047A49E` 與重導向索引從 0 起跑）。2560x1440 已可
穩定進關卡、跑滿整場、零 crash report，這與 sidecar 容量或表面尺寸
的後續修補無關——閃退修復在那些修補之前就已經生效。

**已用獨立驗證排除的環節（不要重查）**：
- 輸出路徑：`SetDIBitsToDevice` 每幀送出完整 2560 寬正確影像
- 引擎的 2048×2048 表面：已放大到 2560×2048，記憶體讀取確認生效，畫面無改善
- `+0x4C8` 矩形容器模型：已證實不存在

**仍未查的環節**：把地形資料光柵化寫進那塊 2560 寬緩衝區的程式碼路徑。
今天完全沒有進去看過。下一輪若要繼續原生高解析度這條路，應該從這裡開始，
而不是回頭重驗上面任何一個已排除的假設。
